<span id="_Toc52661346" class="anchor"></span>Introducción
1.1 Propósito

El propósito de este documento es describir la visión del proyecto SchemaSafe NoSQL, presentando de manera general el problema que se pretende resolver, los interesados y usuarios involucrados, las características principales del producto, sus restricciones y los criterios de calidad esperados. Este documento sirve como base de referencia para el equipo de desarrollo y para el docente del curso, orientando las decisiones de diseño y las prioridades de implementación a lo largo del proyecto.

1.2 Alcance

Este documento describe la visión de SchemaSafe NoSQL, un sistema multimotor orientado al análisis preventivo de riesgos, impacto y compatibilidad de cambios estructurales en bases de datos NoSQL antes de su despliegue. El alcance de la versión descrita en este documento comprende:

Compatibilidad inicial con tres motores NoSQL: MongoDB, Apache CouchDB y Apache Cassandra.
Análisis preventivo (dry-run) de al menos diez tipos de modificaciones estructurales.
Implementación de un motor de reglas de riesgo (mínimo quince reglas) con clasificación BAJO, MEDIO, ALTO y CRÍTICO.
Generación de reportes, historial de análisis, usuarios, roles y auditoría.
Quedan fuera del alcance de esta versión: la ejecución automática de migraciones, la corrección directa de datos incompatibles y la compatibilidad con motores NoSQL adicionales a los tres mencionados, aspectos que se consideran como trabajo futuro habilitado por la arquitectura extensible del sistema.

1.3 Definiciones, Siglas y Abreviaturas

Término	Definición
NoSQL	Bases de datos no relacionales, que incluyen modelos documentales, clave-valor, columnares y orientados a grafos
CQL	Cassandra Query Language, lenguaje utilizado para definir y consultar estructuras en Apache Cassandra
JSON Schema	Mecanismo utilizado por MongoDB para definir reglas de validación sobre documentos
Dry-run	Modo de análisis preventivo en el que un cambio se evalúa sin ejecutarse realmente sobre la base de datos
Adaptador	Componente encargado de interpretar las características de un motor NoSQL específico y transformarlas a un modelo común
Modelo intermedio común	Representación unificada de la información estructural obtenida desde distintos motores NoSQL
Riesgo BAJO/MEDIO/ALTO/CRÍTICO	Niveles utilizados para clasificar el impacto potencial de un cambio estructural
APROBADO / REQUIERE REVISIÓN / NO RECOMENDADO	Resultados generales posibles de un análisis realizado por el sistema
UPT	Universidad Privada de Tacna

Las referencias bibliográficas utilizadas para la elaboración de este documento se detallan en la sección de Bibliografía del presente documento, e incluyen la documentación oficial de MongoDB, Apache CouchDB y Apache Cassandra, así como el sílabo del curso Base de Datos II (SI-783) de la Universidad Privada de Tacna.

<span id="_Toc52661347" class="anchor"></span>Posicionamiento

2.1 Oportunidad de negocio

Actualmente, el análisis del impacto de cambios estructurales en bases de datos NoSQL depende de herramientas específicas de cada gestor o de verificaciones manuales realizadas por desarrolladores y administradores, lo que impide contar con un procedimiento común aplicable a distintos motores. Esta carencia representa una oportunidad para desarrollar una herramienta que unifique el análisis preventivo entre motores documentales, distribuidos y columnares, permitiendo anticipar riesgos antes de que un cambio sea aplicado, en lugar de detectarlos durante la migración, las pruebas o después del despliegue. SchemaSafe NoSQL aprovecha esta oportunidad al ofrecer una capa de análisis multimotor, extensible y explicable, que no reemplaza las herramientas nativas de cada gestor sino que las complementa con una evaluación previa y uniforme del riesgo.

2.2 Definición del problema

	
El problema de	la ausencia de un mecanismo unificado y preventivo para evaluar el riesgo, impacto y compatibilidad de cambios estructurales en múltiples motores de bases de datos NoSQL
Afecta a	desarrolladores y administradores de bases de datos que gestionan la evolución de esquemas en aplicaciones basadas en MongoDB, Apache CouchDB y Apache Cassandra
El impacto de esto es	la aparición de incompatibilidades entre datos existentes y nuevas estructuras, errores en las aplicaciones, fallas durante migraciones y la necesidad de corregir información o desarrollar procesos adicionales una vez que el problema ya se manifestó
Una solución exitosa sería	contar con una herramienta multimotor capaz de analizar preventivamente, bajo un enfoque dry-run, los cambios estructurales propuestos sobre distintos gestores NoSQL, clasificando su nivel de riesgo mediante reglas explícitas y explicables, y cuantificando el impacto sobre los datos existentes antes de que el cambio sea aplicado

4. <span id="_Toc52661349" class="anchor"></span>**Estudio de Factibilidad**

4.1 Perspectiva del producto

SchemaSafe NoSQL es un sistema independiente que se integra con motores NoSQL existentes (MongoDB, Apache CouchDB y Apache Cassandra) mediante conexiones configurables, sin sustituir a dichos gestores ni a sus herramientas nativas de migración. El producto actúa como una capa adicional de análisis previo, ubicada entre el usuario y las bases de datos NoSQL, y no como un componente permanente dentro del flujo de producción de una aplicación.

No requiere modificar las aplicaciones existentes que consumen las bases de datos analizadas, ya que solo realiza operaciones de lectura sobre la información y las estructuras evaluadas.

4.2 Resumen de capacidades

| Capacidad | Beneficio |
|---|---|
| Conexión multimotor (MongoDB, CouchDB, Cassandra) | Un solo sistema para analizar distintos gestores NoSQL |
| Exploración de estructuras existentes | Identificación automática de atributos, tipos, índices y validaciones |
| Definición de cambios estructurales propuestos | Evaluación previa sin ejecutar el cambio |
| Motor de reglas de riesgo (mínimo 15 reglas) | Clasificación explicable en BAJO/MEDIO/ALTO/CRÍTICO |
| Cálculo de impacto (cantidad y porcentaje) | Dimensiona objetivamente la magnitud del riesgo |
| Modelo intermedio común | Uniformiza el análisis entre motores con características distintas |
| Reportes detallados | Documentación clara del análisis para tomar decisiones |
| Historial y comparación de análisis | Seguimiento de la evolución de una estructura en el tiempo |
| Usuarios, roles y auditoría | Control de acceso y trazabilidad de las operaciones realizadas |
| Arquitectura extensible por adaptadores | Incorporación futura de nuevos motores NoSQL |

4.3 Suposiciones y dependencias

Suposiciones:
- Las bases de datos utilizadas para las pruebas serán bases de datos controladas o de desarrollo, generadas específicamente para el proyecto.
- Los usuarios cuentan con conocimientos básicos sobre la estructura de las bases de datos NoSQL que administran.
- Las instancias de MongoDB, CouchDB y Cassandra utilizadas estarán disponibles localmente o en un entorno accesible durante el desarrollo y las pruebas.
- Las conexiones utilizadas para el análisis dispondrán únicamente de permisos de lectura.

Dependencias:
- Motores NoSQL: MongoDB, Apache CouchDB y Apache Cassandra (versiones estables vigentes al momento del desarrollo).
- Drivers/conectores oficiales de cada motor para el lenguaje de programación seleccionado.
- Un motor de base de datos adicional para almacenar el historial de análisis, usuarios, roles y auditoría del propio sistema.
- Disponibilidad de un entorno de desarrollo con soporte para contenedores (por ejemplo, Docker) para desplegar instancias de prueba de los tres gestores.

4.4 Costos y precios

Al tratarse de un proyecto académico desarrollado con fines de investigación y aprendizaje, no se contempla un modelo comercial de precios. Los costos considerados corresponden principalmente a:

- Tiempo de desarrollo del equipo del proyecto.
- Uso de herramientas y tecnologías de software libre (MongoDB Community, Apache CouchDB, Apache Cassandra son de uso gratuito bajo sus respectivas licencias).
- Infraestructura de pruebas (equipos propios o entornos virtualizados/contenedores), sin costo adicional de licenciamiento.

No se generan costos de licenciamiento por el uso de los motores NoSQL seleccionados, dado que todos ellos cuentan con versiones de uso libre.

4.5 Licenciamiento e instalación

- El sistema SchemaSafe NoSQL será distribuido, en su versión de prototipo, como software académico sin fines comerciales.
- Los motores NoSQL utilizados (MongoDB, Apache CouchDB, Apache Cassandra) se rigen por sus propias licencias de código abierto.
- La instalación del sistema requerirá: el entorno de ejecución correspondiente al lenguaje/framework elegido, acceso a las instancias de los motores NoSQL configurados y la base de datos interna donde se almacenará el historial, los usuarios y la auditoría.
- Se recomienda su instalación en entornos de desarrollo o pruebas, dado que el sistema requiere credenciales con permisos de lectura sobre las bases de datos que analiza.

5. <span id="_Toc52661350" class="anchor"></span>**Características del producto**

5.1 Características generales

- Conexión configurable con MongoDB, Apache CouchDB y Apache Cassandra mediante adaptadores independientes.
- Verificación del estado de conexión con cada motor antes de iniciar un análisis.
- Exploración de bases de datos, colecciones, documentos, tablas y demás estructuras según el gestor seleccionado.
- Obtención automática de la estructura actual de los datos (atributos, tipos, estructuras anidadas, índices, validaciones y restricciones).
- Identificación de atributos representados con distintos tipos de datos dentro de un mismo conjunto de información.
- Modelo intermedio común para representar de forma uniforme la información obtenida desde los distintos motores.
- Definición de cambios estructurales propuestos sin ejecutarlos sobre la base de datos.
- Cálculo automático de la cantidad y el porcentaje de elementos potencialmente afectados por cada cambio.
- Explicación de las causas que originan cada nivel de riesgo y generación de recomendaciones preventivas.
- Resultado general del análisis: APROBADO, REQUIERE REVISIÓN o NO RECOMENDADO.
- Enfoque de análisis preventivo (dry-run), sin ejecutar modificaciones sobre la base analizada.
- Generación de reportes detallados y mantenimiento de un historial comparable de análisis.
- Gestión de usuarios, roles y auditoría de las operaciones principales.
- Arquitectura extensible mediante adaptadores para incorporar nuevos motores NoSQL en el futuro.

5.2 Tipos de modificaciones estructurales analizadas

1. Incorporación de nuevos atributos o campos.
2. Eliminación de atributos existentes.
3. Renombramiento de atributos.
4. Modificación de tipos de datos de un atributo.
5. Establecimiento de atributos como obligatorios.
6. Modificación de estructuras anidadas (por ejemplo, de campo simple a objeto anidado).
7. Cambios relacionados con índices.
8. Incorporación o modificación de validaciones.
9. Cambios sobre restricciones soportadas por el motor.
10. Modificaciones estructurales específicas de cada gestor NoSQL (por ejemplo, cambios de tipo de columna en Cassandra).

5.3 Reglas de evaluación de riesgo

El motor de análisis de SchemaSafe implementará como mínimo quince reglas, agrupadas según el aspecto que evalúan. Cada regla genera una causa explicable que se incluye en el reporte final.

**Reglas sobre tipos de datos**
1. El atributo modificado presenta un tipo de dato distinto al propuesto en más del 50 % de los registros analizados → riesgo ALTO.
2. El atributo modificado presenta un tipo de dato distinto al propuesto en un porcentaje menor al 50 % pero mayor al 10 % → riesgo MEDIO.
3. Coexisten tres o más tipos de datos distintos para un mismo atributo dentro de la misma colección/tabla → riesgo ALTO.
4. El nuevo tipo de dato no admite conversión automática desde el tipo actual (por ejemplo, texto no numérico → entero) → riesgo CRÍTICO.

**Reglas sobre atributos obligatorios y ausentes**
5. Se propone un atributo obligatorio y existe al menos un registro que no lo contiene → riesgo MEDIO (proporcional al porcentaje de registros sin el atributo).
6. El porcentaje de registros sin el atributo obligatorio propuesto supera el 30 % → riesgo ALTO.
7. Se detectan valores nulos en un atributo que se propone como obligatorio o no-nulo → riesgo MEDIO o ALTO según el porcentaje afectado.

**Reglas sobre eliminación y renombramiento**
8. Se propone eliminar un atributo presente en más del 20 % de los registros → riesgo ALTO.
9. Se propone eliminar un atributo presente en más del 80 % de los registros → riesgo CRÍTICO.
10. Se propone renombrar un atributo ampliamente utilizado (por encima de un umbral configurable) sin evidencia de actualización de las consultas dependientes → riesgo ALTO.

**Reglas sobre estructuras anidadas**
11. Se propone transformar un atributo simple en una estructura anidada y el atributo es utilizado por un porcentaje significativo de registros → riesgo ALTO.
12. La estructura anidada propuesta introduce niveles adicionales de profundidad no presentes en los datos actuales → riesgo MEDIO.

**Reglas sobre índices, validaciones y restricciones**
13. Se propone una validación o restricción que los datos existentes no cumplen actualmente → riesgo ALTO o CRÍTICO según el porcentaje de incumplimiento.
14. Se propone eliminar o modificar un índice utilizado activamente por consultas conocidas del sistema → riesgo MEDIO.
15. Se propone una característica no soportada por el motor NoSQL seleccionado → el sistema señala la limitación y omite la evaluación cuantitativa para esa regla.

**Reglas específicas por motor**
16. (Cassandra) Cambio de tipo de una columna que forma parte de la clave primaria o de partición → riesgo CRÍTICO.
17. (MongoDB/CouchDB) Modificación de un campo utilizado en una regla de validación de esquema (JSON Schema) existente → riesgo ALTO.

Este conjunto de reglas podrá ampliarse durante el desarrollo del proyecto a partir de los escenarios de prueba identificados, manteniendo siempre el mínimo de quince reglas exigido por los objetivos del proyecto.

<div style="page-break-after: always; visibility: hidden">\pagebreak</div>

6. <span id="_Toc52661351" class="anchor"></span>**Restricciones**

- El sistema trabajará inicialmente solo con tres motores NoSQL: MongoDB, Apache CouchDB y Apache Cassandra.
- El análisis se realizará únicamente bajo un enfoque preventivo (dry-run); el sistema no ejecutará automáticamente los cambios estructurales evaluados.
- Las conexiones utilizadas durante los análisis deberán limitarse, siempre que sea posible, a permisos de solo lectura.
- Determinadas comprobaciones (índices, validaciones, restricciones) estarán disponibles únicamente cuando el motor NoSQL seleccionado soporte dicha característica.
- Las pruebas del sistema se realizarán exclusivamente sobre bases de datos controladas o generadas para el proyecto, sin utilizar información de sistemas reales o productivos.
- El sistema no reemplaza herramientas de migración de datos ni ejecuta transformaciones automáticas sobre las bases analizadas.
- El desarrollo del proyecto está limitado por el cronograma y los recursos disponibles dentro del curso de Base de Datos II (SI-783) de la UPT.
- La cobertura de reglas de análisis dependerá de las características documentadas de cada motor al momento del desarrollo.

7. <span id="_Toc52661352" class="anchor"></span>**Rangos de Calidad**

| Atributo de calidad | Rango / criterio esperado |
|---|---|
| Exactitud del análisis | Detección del 100 % de los escenarios críticos definidos en las pruebas controladas |

| Explicabilidad | Cada clasificación de riesgo debe incluir al menos una causa documentada |
| No intrusividad | 0 modificaciones ejecutadas automáticamente sobre las bases de datos analizadas durante las pruebas |
| Extensibilidad | Incorporación de un nuevo motor NoSQL sin modificar el núcleo del sistema, solo mediante un nuevo adaptador |
| Disponibilidad de conexión | Verificación del estado de conexión con cada motor antes de iniciar cualquier análisis |
| Trazabilidad | Registro de auditoría del 100 % de las operaciones de análisis realizadas |
| Usabilidad | Reportes comprensibles sin requerir conocimiento previo del motor de reglas interno |
| Rendimiento (referencial) | Análisis de colecciones/tablas de prueba de hasta 10 000 registros en tiempos razonables para un entorno de desarrollo |
| Cobertura de reglas | Mínimo 15 reglas de evaluación de riesgo implementadas y verificadas |

8. <span id="_Toc52661353" class="anchor"></span>**Precedencia y Prioridad**

| Orden | Funcionalidad | Prioridad | Justificación |
|---|---|---|---|
| 1 | Arquitectura de adaptadores y modelo intermedio común | Alta | Es la base estructural sobre la que dependen todas las demás funcionalidades |
| 2 | Conexión y exploración de estructuras (MongoDB, CouchDB, Cassandra) | Alta | Necesaria para obtener la información que será analizada |
| 3 | Definición de cambios estructurales propuestos | Alta | Habilita la evaluación preventiva, núcleo del proyecto |
| 4 | Motor de reglas y clasificación de riesgo (BAJO/MEDIO/ALTO/CRÍTICO) | Alta | Constituye el valor central de SchemaSafe |
| 5 | Cálculo de impacto (cantidad y porcentaje afectado) | Alta | Complementa directamente la clasificación de riesgo |
| 6 | Generación de reportes | Media | Necesaria para comunicar los resultados al usuario |
| 7 | Historial de análisis y comparación de versiones | Media | Aporta valor de seguimiento, pero no bloquea el análisis inicial |
| 8 | Usuarios, roles y auditoría | Media | Requerida para un uso controlado, pero independiente del motor de análisis |
| 9 | Reglas específicas por motor (particularidades de Cassandra, CouchDB) | Baja-Media | Complementa la cobertura, pero puede evolucionar después de las reglas generales |
| 10 | Soporte para motores NoSQL adicionales (Redis, Neo4j, etc.) | Baja | Fuera del alcance inicial; queda como trabajo futuro habilitado por la arquitectura |

9. <span id="_Toc52661354" class="anchor"></span>**Otros requerimientos del producto**

- El sistema deberá documentar las funcionalidades disponibles y las limitaciones existentes para cada uno de los motores NoSQL implementados.
- Deberá permitir distinguir claramente entre reglas generales (aplicables a varios motores) y reglas específicas (propias de un gestor determinado).
- Los adaptadores deberán entregar al núcleo del sistema información normalizada, independientemente de las particularidades de cada motor.
- El sistema deberá contemplar mecanismos de manejo de errores ante fallas de conexión con los motores NoSQL, sin afectar la integridad de los análisis ya registrados.
- Se deberá considerar el idioma español como idioma principal de la interfaz y de los reportes generados.
- El sistema deberá permitir la exportación o consulta posterior de los reportes generados, para su uso como evidencia dentro del proceso de desarrollo.
- Se recomienda considerar buenas prácticas de seguridad en el manejo de credenciales de conexión hacia los motores NoSQL (por ejemplo, evitar almacenarlas en texto plano).

<span id="_Toc52661355" class="anchor"></span>**CONCLUSIONES**

- La flexibilidad estructural que caracteriza a las bases de datos NoSQL no elimina los riesgos asociados a la evolución de sus esquemas; por el contrario, dicha flexibilidad puede ocultar incompatibilidades que solo se manifiestan durante la ejecución de una migración o el despliegue de una nueva versión de la aplicación.
- Cada motor NoSQL analizado (MongoDB, Apache CouchDB y Apache Cassandra) presenta mecanismos propios para estructurar, validar y modificar sus datos, lo que hace inviable aplicar una única estrategia de análisis sin un modelo intermedio común.
- La arquitectura basada en adaptadores permite separar las particularidades de cada motor del núcleo de análisis, facilitando tanto el mantenimiento del sistema como la incorporación futura de nuevos gestores NoSQL.
- Un enfoque de análisis preventivo (dry-run), basado en reglas explícitas y explicables, permite anticipar el impacto de un cambio estructural sin poner en riesgo la información existente, dando al usuario la posibilidad de tomar decisiones informadas antes de modificar una base de datos.
- La cuantificación del impacto mediante cantidad y porcentaje de elementos afectados aporta un criterio objetivo para clasificar los cambios y priorizar las acciones correctivas necesarias.

<div style="page-break-after: always; visibility: hidden">\pagebreak</div>

<span id="_Toc52661356" class="anchor"></span>**RECOMENDACIONES**

- Ampliar progresivamente el conjunto de reglas de análisis a medida que se identifiquen nuevos patrones de riesgo durante las pruebas con escenarios controlados.
- Evaluar, en versiones posteriores del proyecto, la incorporación de motores NoSQL adicionales (como Redis o Neo4j) aprovechando la arquitectura extensible basada en adaptadores.
- Mantener siempre conexiones de solo lectura durante los análisis, reforzando el principio de no intrusividad del sistema sobre las bases de datos evaluadas.
- Documentar de forma continua las limitaciones específicas de cada motor NoSQL, de manera que los usuarios comprendan qué comprobaciones están disponibles según el gestor seleccionado.
- Considerar la integración de SchemaSafe con procesos de integración continua (CI/CD), de modo que el análisis preventivo pueda ejecutarse automáticamente antes de un despliegue.
- Validar el sistema con conjuntos de datos cada vez más diversos y de mayor volumen, con el fin de comprobar su comportamiento en escenarios más cercanos a entornos reales.
